# План добавления IPv6

Дата: 2026-11-15. Статус: план, реализация не начата.

## Цель и границы первого выпуска

Добавить опциональный dual-stack режим: существующая публикация IPv4 продолжает
работать, IPv6 включается отдельно. Сохраняем BIRD и одного принимающего peer,
которому передаются оба семейства маршрутов. Приложение публикует маршруты;
IPv6 в LAN, VPN и обратный маршрут настраиваются на сетевых устройствах отдельно.

Первый выпуск охватывает генерацию IPv6 из всех штатных видов источников,
передачу по BGP, предпросмотр, объяснение IP, мониторинг и восстановление.
IPv6-only установки, несколько peer, link-local peering с zone ID и передача
префиксов с next hop другого семейства остаются за пределами первого выпуска.
Обсуждаемый DNS-прокси остаётся отдельной доработкой; IPv6 не зависит от него.

## Исходное состояние

- `generate_routes.collapse_routes()` уже разделяет семейства. Но извлечение
  адресов из источников использует IPv4 regex и добавляет `/32` к одиночным IP.
- `sources/domains.py` и `dns_resolver.py` получают только A-записи;
  страны, Google ranges и provenance обрабатываются как IPv4.
- Штатный BIRD-шаблон содержит IPv4 static protocol и одну IPv4 BGP-сессию.
- Применение, подтверждённые снапшоты, поиск маршрутов и объяснение IP требуют
  расширения на два семейства. Address List экспорт намеренно ограничен IPv4.
- Проверки окружения, сетевые диагностики, Compose и часть интерфейса также
  предполагают IPv4. Настройка `enable_ipv6: false` в bridge-сети требует
  отдельной проверки для dev-окружения; рабочая установка использует host network.

## 1. Зафиксировать настройки и совместимость

- Добавить выключенный по умолчанию `IPV6_ENABLED`, адреса `BIRD_IPV6`,
  `PEER_IPV6` и имя `BGP_PROTOCOL_IPV6`. Это предлагаемые имена новых настроек.
- Использовать те же `MY_AS`, `PEER_AS` и community. Существующие IPv4-настройки,
  алиасы `MT_*`, имя IPv4-протокола и пути файлов сохраняют своё значение.
- Оставить `ROUTER_ID` 32-битным идентификатором в IPv4-нотации.
- Проверять обязательные IPv6-настройки только при включении режима;
  проверять наличие локального адреса и уникальность имён BGP-протоколов.
- Расширить схему панели, `.env.example`, оба стека Compose и shell-окружение.
  Старые настройки и бэкапы получают `IPV6_ENABLED=0` при чтении/импорте.
- Пользовательский BIRD-шаблон без поддержки IPv6 продолжает работать при
  выключенном режиме; при включении выдаётся понятная ошибка с инструкцией.

Готовность: старая конфигурация запускается без новых параметров и получает
прежний IPv4-набор; валидация IPv6 не меняет работающую конфигурацию при ошибке.

## 2. Обобщить обработку адресов и сборку маршрутов

- Вынести общий разбор IP/CIDR для генератора, check-IP, источников и экспорта.
  Одиночные адреса превращать в `/32` или `/128` по семейству.
- Обрабатывать текстовые и поддерживаемые JSON-источники без случайного
  извлечения IPv4-части из IPv4-mapped IPv6 или фрагмента некорректной записи.
- Нормализовать сжатую IPv6-запись; сортировать, агрегировать и вычитать
  исключения отдельно для IPv4 и IPv6. Исправить `subtract_networks()` для
  смешанных входных данных.
- Сохранять общие пользовательские списки, поддерживающие оба семейства;
  выключенный IPv6 не должен менять результат IPv4 или считаться ошибкой данных.
- Добавить отдельный порог длины IPv6-префикса и лимиты количества маршрутов
  и разрастания при исключениях. Конкретные значения закрепить тестовыми
  примерами до включения режима. `::/0` отклонять явно.

Готовность: смешанный источник даёт два корректных набора, исключение `/128`
не возвращается при агрегации, превышение лимита сохраняет действующие маршруты.

## 3. Расширить источники и DNS

- URL и ASN: извлекать IPv6 из реального формата ответа; добавить фикстуры
  ответов текущих провайдеров и явную диагностику источника только с IPv4.
- Страны: читать `resources.ipv6` RIPEstat и IPv6 delegated stats. У IPv6
  поле `value` означает длину префикса, а не количество адресов, как у IPv4.
- Google: читать `ipv6Prefix` и отдельно вычитать IPv6 Cloud ranges.
- Домены и URL-списки доменов: получать A и AAAA; различать успешное отсутствие
  AAAA и ошибку DNS. Отсутствие AAAA само по себе не является сбоем.
- Хранить результаты A/AAAA раздельно, чтобы старый IPv4-кеш не считался
  полноценным IPv6-результатом. Подтверждённое исчезновение AAAA должно отзывать
  прежний адрес, а не бесконечно возвращать его из кеша.
- Сохранять строгую обработку ошибок исключений: если их актуальное состояние
  нельзя установить и пригодного кеша нет, новый набор не применять.
- В первом выпуске AAAA разрешено запрашивать у существующих IPv4 DNS-серверов.
  IPv6-транспорт до DNS и HTTP-источников не является условием получения IPv6-маршрутов.
  Для собственного DNS-клиента проверить усечение UDP и fallback на TCP.

Готовность: все штатные источники проверены на обоих семействах, включая
отсутствие IPv6, сбой источника, кеш и ошибку обязательного исключения.

## 4. Добавить публикацию IPv6 в BIRD

- Создать отдельный IPv6 static protocol и отдельную BGP-сессию поверх IPv6
  к тому же роутеру. IPv4-сессия сохраняет текущую конфигурацию.
- Добавить IPv6-фильтр экспорта с community и корректным IPv6 next hop;
  входящие маршруты по-прежнему не принимать.
- Сохранить существующий `routes.conf` как IPv4-файл; добавить отдельный
  IPv6-файл. Не помещать IPv6 в файл, используемый старым IPv4 static protocol.
- Проверять конфигурацию BIRD до применения. При отключении режима явно
  отзывать IPv6-анонсы и не восстанавливать их из старого снапшота при старте.
- Диагностировать обе сессии отдельно. Готовность и healthcheck должны учитывать
  только включённые семейства и действующую настройку требования BGP;
  ошибка IPv6-сессии не должна уничтожать работающий IPv4-набор.

Готовность: BIRD и FRR устанавливают обе сессии, а принимающая сторона видит
правильные community и next hop для каждого семейства.

## 5. Расширить снапшоты, применение и восстановление

- Подготавливать оба набора под общей блокировкой, не меняя активные файлы
  до завершения генерации и проверок.
- Добавить версионированный манифест поколения с хешами обоих наборов и
  provenance. Существующие IPv4-файлы и sidecar сохранять совместимыми;
  старый снапшот трактовать как IPv4 без IPv6.
- Для первого выпуска выбрать общее применение: ошибка обязательного источника
  или применения любого включённого семейства сохраняет предыдущую пару наборов.
  Успех публиковать только после принятия всей конфигурации BIRD.
- Предусмотреть восстановление после остановки между записью файлов,
  принятием BIRD и публикацией манифеста; не принимать пару из разных поколений.
- Привязать предпросмотр к конфигурации и обоим действующим наборам;
  применять именно просмотренный результат. Старые предпросмотры после
  изменения формата/режима отклонять с предложением создать новый.
- Различать корректно пустое семейство, массовый отзыв и сбой генерации.
  Пустой IPv6 из IPv4-only источников допустим; неожиданное обнуление ранее
  непустого IPv6 требует явного подтверждения в предпросмотре. Пустой файл
  сам по себе не должен означать неисправность BIRD.
- Проверить обновление и откат образа: возврат к версии без IPv6 должен
  восстанавливать прежние настройки и IPv4, явно сообщая об отзыве IPv6.

Готовность: ошибки и аварийный перезапуск не публикуют смешанный снапшот,
а ошибка IPv6-генерации не заменяет рабочие IPv4-маршруты новым частичным набором.

## 6. Панель, API, метрики и экспорт

- Добавить переключатель IPv6 и отдельные адреса/статусы сессии.
- Показывать счётчики, изменения предпросмотра, возраст подтверждённого набора
  и ошибки по семействам. Смысл старых IPv4-полей API и метрик сохранять;
  для IPv6 и общего итога добавить явные новые поля/метрики.
- Расширить check-IP, объяснение источников, поиск IP/CIDR и сетевую диагностику.
  В JavaScript не представлять 128-битные адреса обычным `Number`;
  использовать серверный поиск либо корректное 128-битное представление.
- Сохранить прежние IPv4-выгрузки и добавить скачивание IPv6 routes-файла.
  IPv6 Address List для RouterOS оформить отдельной следующей задачей;
  текущий IPv4 `.rsc` обязан работать при включённом dual-stack.
- Обновить backup/import, переводы RU/EN и мобильное отображение длинных адресов.

Готовность: результат проверки IPv6 объясняется подтверждённым снапшотом,
IPv4 API/экспорт работают как прежде, интерфейс не смешивает ошибки двух семейств.

## 7. Проверки и выпуск

1. Unit-тесты: IPv4-регрессии, IPv6/смешанный разбор, `/128`, `::/0`, агрегация,
   исключения, лимиты, A/AAAA и кеш, provenance, миграция и откат снапшотов.
2. Проверки отказов: ошибка IPv6-генерации, отказ BIRD, разрыв IPv6 BGP,
   остановка между стадиями записи, устаревший предпросмотр, включение/отключение.
3. Docker BIRD + FRR: dual-stack сеть, две сессии, community, запрет default route,
   правильный VPN next hop и установка IPv6 в Linux FIB, замена и отзыв маршрутов.
4. Изолированный тест передачи IPv6-трафика через тестовый туннель; отдельно
   проверить реальный MikroTik с IPv6 VPN, обратным маршрутом и Path MTU Discovery.
   Established без проверки FIB и клиентского трафика недостаточно.
5. JS/браузерные проверки: поиск IPv6, предпросмотр, диагностика, настройки,
   ошибки, импорт старого бэкапа, длинные адреса на мобильном экране.
6. Документация RU/EN: требования IPv6 LAN/VPN, BIRD, FRR и RouterOS;
   отсутствие IPv6 VPN не должно маскироваться успешной BGP-сессией.
7. Перед релизом выполнить `python -m unittest discover -s tests`, JS,
   браузерные и Docker-проверки; выпускать с IPv6 выключенным по умолчанию.

## Последовательность изменений

1. Общий IP/CIDR-парсер и модель двух семейств без включения IPv6 в работе.
2. Источники, AAAA и кеши с тестами.
3. Совместимые снапшоты и общая транзакция применения.
4. BIRD, окружение, Compose и проверки BIRD/FRR.
5. Панель, API, диагностика, метрики и совместимость экспорта/бэкапов.
6. Сквозные проверки, инструкция MikroTik/FRR и пилотное включение.
