# Подключение BGP peer

[Установка](../README.md) | [FRRouting](frr.md) | [MikroTik](mikrotik.md) | [English](bgp.en.md)

BGP Antifilter передаёт IPv4-префиксы по стандартному BGP. Принимающей стороной может быть маршрутизатор или сервер с BGP. Для него нужны фильтры community и возможность направить принятые маршруты на VPN-шлюз. Готовые примеры: [FRR](frr.md) и [RouterOS](mikrotik.md). Совместимость с каждой другой платформой следует проверять отдельно.

## Схема

```text
Источники → BGP Antifilter / BIRD → IPv4 BGP → ваш маршрутизатор → VPN
```

Приложение управляет списками и анонсами, а маршрутизатор — передачей трафика. VPN настраивается заранее.

**На принимающей стороне обязательно задайте VPN next hop.** BIRD анонсирует свой `BIRD_IP` как следующий узел. Локальные маршруты приложения имеют тип `blackhole`: Linux-сервер с приложением не является VPN-шлюзом и сам этот трафик не пересылает.

## Настройки приложения

| Параметр | Пример | Назначение |
| --- | --- | --- |
| `MY_AS` | `64500` | AS приложения |
| `PEER_AS` | `65455` | AS принимающей стороны |
| `PEER_IP` | `192.168.55.1` | Доступный адрес BGP peer |
| `BIRD_IP` | `192.168.55.5` | Адрес Linux-сервера, уже назначенный его интерфейсу |
| `ROUTER_ID` | `192.168.55.5` | Router ID BIRD |
| `BGP_COMMUNITY` | `65432,500` | Метка маршрутов; у peer записывается как `65432:500` |
| `BGP_PROTOCOL` | `mikrotik` | Внутреннее имя сессии BIRD, сохранённое для совместимости |

Имя `mikrotik` не ограничивает платформу peer. В штатном шаблоне можно задать другое имя через `BGP_PROTOCOL`; для собственного шаблона имя в конфигурации и настройках проверки должно совпадать. Изменения BGP-настроек в панели требуют пересоздания контейнера.

Штатный шаблон содержит один BGP peer. Примеры используют eBGP с разными AS; iBGP в этих примерах не проверяется. Используется multihop, TCP 179 должен быть доступен между указанными адресами. Ограничьте доступ к этому порту адресом peer. IPv6-анонсы и настройка нескольких peer через панель пока не поддерживаются.

## Политика принимающей стороны

1. Принимать только IPv4-префиксы с настроенной community.
2. Отклонять маршрут по умолчанию; пример FRR принимает длины от /8 до /32, как стандартная защита генератора.
3. Назначать VPN-шлюз вместо `BIRD_IP`; этот шлюз должен разрешаться через таблицу маршрутизации принимающей стороны.
4. Запрещать отправку собственных маршрутов в приложение. BIRD со своей стороны также использует `import none`.
5. Настроить пересылку IPv4, VPN, firewall и при необходимости NAT на маршрутизаторе. Согласовать адресные ограничения VPN-пира с выбранными префиксами.

## Проверка

```bash
docker compose exec bgp-antifilter birdc show protocols
docker compose exec bgp-antifilter birdc show route count
```

Ожидаются Established, непустой список и статус healthy. На принимающей стороне проверьте community, VPN next hop и установку маршрута в системную таблицу. Затем проверьте реальный доступ с устройства за маршрутизатором: одна установленная BGP-сессия не подтверждает передачу трафика через VPN.

## Совместимость настроек

- `MT_IP` и `MT_AS` продолжают работать как старые имена для `PEER_IP` и `PEER_AS`.
- В одной группе переменных окружения `PEER_*` имеет приоритет над `MT_*`. Compose передаёт также согласованные `MT_*`, поэтому новый стек может использовать прежний образ приложения.
- Сохранённые настройки панели имеют приоритет над окружением контейнера, в том числе старые настройки с `MT_*`. При следующем сохранении используются имена `PEER_*`.
- Старые JSON-копии конфигурации принимаются и преобразуются при импорте; противоречащие друг другу пары старых и новых имён отклоняются.
- В командном окружении остаются оба набора имён с одинаковыми значениями, поэтому прежние пользовательские шаблоны BIRD сохраняют работу.
- Имя сессии `mikrotik` по умолчанию сохранено для старых шаблонов, healthcheck и внешних скриптов.

Экспорт Address List `.rsc` — отдельная возможность для RouterOS; он описан в [инструкции MikroTik](mikrotik.md#address-list-вместо-bgp).
