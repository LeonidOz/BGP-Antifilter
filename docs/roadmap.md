# Возможные доработки

Идеи для будущих версий; сроки и состав реализации пока не определены.

## Опциональная поддержка IPv6

Добавлено: 2026-11-15. Статус: составлен [план реализации](ipv6-plan.md).

Добавить dual-stack режим с IPv6-источниками, AAAA, отдельной BGP-сессией,
совместимыми снапшотами, предпросмотром и диагностикой. IPv6 по умолчанию выключен;
существующая работа IPv4 сохраняется.

## Опциональный DNS-прокси для устройств LAN

Добавлено: 2026-11-15. Статус: предложение на будущее.

Добавить отдельный опциональный режим DNS-прокси, к которому устройства
обращаются напрямую. MikroTik получает маршруты по BGP и направляет трафик;
его DNS-сервер в этой схеме не используется.

```text
Устройства → DNS-прокси BGP-Antifilter → upstream DNS (например AdGuard Home)
                      └─ маршруты из DNS-ответов → BIRD → BGP → MikroTik
```

Основные требования к будущему режиму:

- По умолчанию выключен; включается отдельно от существующей генерации списков.
- Прямые DNS-запросы устройств по UDP/TCP на порту 53; адрес прокси можно
  выдавать клиентам через DHCP.
- Настраиваемый upstream DNS и разрешённые клиентские подсети.
- Динамические IPv4-маршруты по фактическим ответам клиентам с учётом правил
  включения/исключения, TTL и связей CNAME/HTTPS/SVCB.
- Сохранение наблюдённых адресов и восстановление после перезапуска;
  согласование динамических маршрутов с плановым обновлением списков.
- Отдельно продумать отказоустойчивость прямых клиентов: переключение DNS
  самого MikroTik им не помогает. Учесть, что клиентский DoH/DoT обходит прокси.

Референс для изучения: [DNS-прокси в форке Dark-V](https://github.com/Dark-V/BGP-Antifilter/blob/7221df5fa9358208e72a2114fe3f2904971afcbe/docs/adguard-dns.md).
Реализацию потребуется адаптировать к текущей архитектуре проекта. Выбор
механизма передачи динамических маршрутов в BIRD и гарантий готовности
маршрута перед DNS-ответом оставить этапу проектирования.
